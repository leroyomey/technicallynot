---
name: write-skills
description: When an agent saves a reusable procedure as a skill, and which kind (project skill vs Technically Not library skill). Sent only while Settings › Agents › Write skills is on.
for: every-agent
when: write-skills
tnai-hidden: true
---
- Write skills: when a task taught you a procedure that will clearly be needed again (a multi-step workflow, a check recipe, a project convention nobody wrote down), save it as a skill before you finish. Skip it for one-off fixes, anything already covered by a skill, CLAUDE.md, AGENTS.md or the docs, and anything holding secrets. Run `tnai skill list` first and improve an existing skill instead of adding a near-duplicate; `tnai skill overlaps PATH` tells whether a draft covers the same topic as an existing skill, and `tnai skill save` refuses one that does unless you add `--distinct` after reading them.
- Learn from every fix, unasked: after you fix a bug or the user corrects you, ask "which skill or rule should have prevented this?" before you report. When one owns that file or topic, add the lesson there in the same task, as one short rule stating the cause in general terms (not the story of this bug), without being asked; when none does and it could happen again, add it to the doc or skill closest to the topic. "Skip it for one-off fixes" above means no new skill for a one-off, never that the lesson goes unrecorded. Say in your reply which skill you improved, or in one line why none needed it, so the user never has to ask.
- Skills keep improving, with the reason shown: not only after a bug. At the end of every task that followed a skill, ask whether the work showed the skill to be wrong, missing a step, out of date, or slower than what you ended up doing, or whether the user tuned the result. Before you change it, argue it out briefly in your own reasoning, no sub-agent: the case for (what happened in this task, the evidence), the case against (a one-off, already covered, makes the skill longer to read on every later task, goes against a user decision), then the verdict. Change the skill only when the case for wins, as the smallest edit, with the reason in a few words inside the rule ("learned DATE: cause") and the skill's "Last checked" date updated. In the reply write one short "Skill improved" paragraph: which skill, what changed, why, the strongest point against and why it lost; when you weighed a change and dropped it, say that in one line with the reason. In the Technically Not report put "improved skill NAME: what, because why" under "- Decided:" and the file under "- Changed:". Never weaken or remove a user decision in a skill this way; ask instead.
- Pick the kind: a PROJECT skill when it is about this project's code, commands or conventions: write `.claude/skills/<name>/SKILL.md` in the project (it travels with the project in git, and every agent working here can read it). A Technically Not LIBRARY skill when it is a general habit useful in any project: write the SKILL.md in a temp folder and run `tnai skill save <folder>` (it appears on Technically Not's Skills page and a new one is on for every session from the start, so save only what truly helps in any project; the user can switch it off there). Never write to the user's own `~/.claude/skills` or to Technically Not's hidden program skills unless the user asks in their own words.
- A SKILL.md starts with frontmatter `name:` (kebab-case) and `description:` (what it does and when to use it, one or two sentences) and `keywords:` (comma-separated words a prompt about this topic would contain, e.g. `user interface, css layout, button style`; Technically Not points agents to a skill when a prompt mentions its name words or keywords) and, when the skill owns specific files, `paths:` (comma-separated globs such as `src/styles/**`; the skill is offered when an agent opens one of them), then short, concrete steps. Before you report a new or changed skill, run `tnai skill match "TEXT"` on three sentences the user would really say for it and fix the `keywords:` until each one names the skill, then on one everyday sentence that must not name it (a bare common word as a keyword, such as "reply", matches messages that have nothing to do with the skill) (a new library skill is matched once it is saved). So the skill gives the same result whoever follows it, write its body in five parts: when to use it, the numbered steps, the output (the exact shape of what comes back: which file, headings or columns), a "Done when" checklist to tick before reporting, and a "Last checked" date. List what you saved under "- Changed:" in the Technically Not report.
- Consolidate skills on one topic: when you notice two or more skills about the same thing (e.g. several UI skills; `tnai skill overlaps` lists candidate groups with why they match), finish your task first, then read them all. Merge only when they really cover one topic; skills that split an area into distinct jobs with different triggers stay apart. A merge is one skill that keeps every rule, step and user decision from each (nothing dropped or weakened; if two contradict, ask the user), the union of their `keywords:` and `paths:`, a description covering all of it, and the name of the most-read one (the "keep the name" in `tnai skill overlaps`). Then remove the superseded ones: a library skill with `tnai skill remove NAME`; a project skill by deleting its folder and fixing every reference to its name (CLAUDE.md, AGENTS.md, the skill file map, other skills, docs; search the project for the old names). Ask the user before changing or removing a skill the user added or wrote by hand, one that is locked or holds the user's own decisions as its main content, or one outside the project and Technically Not's library. List the merged and removed skills under "- Changed:".
